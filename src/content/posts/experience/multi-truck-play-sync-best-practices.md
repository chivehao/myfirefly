## 0. 前言
无论是视频还是音频，双轨播放都是其相应的应用场景，本文介绍下双轨播放的同步方案的最佳实践。

比如视频的应用场景：同时播放音频轨道、工作人员访谈轨道。
再比如音频的场景：同时播放干声和伴奏。

本文已音频干声和伴奏进行说明。

## 1. 设计目标

首页播放时，以伴奏轨作为同步参考，控制干声轨与伴奏轨保持稳定同步。干声和伴奏允许原本总时长不一致，不能因为较短轨道已经结束而持续触发重同步。

同步误差分级如下：

| 相对误差 | 处理方式 |
| --- | --- |
| `±5ms` 以内 | 达到目标，不做校正 |
| 超过 `±5ms` 且不超过 `±10ms` | 小幅速率微调 |
| 超过 `±10ms` 且不超过 `±50ms` | 中幅速率微调 |
| 超过 `±50ms` 且不超过 `±100ms` | 较大幅度速率微调 |
| 超过 `±100ms` 且不超过 `±200ms` | 更大幅度速率微调 |
| 超过 `±200ms` | 发起一次串行 seek 重同步；等待 `seeked` 完成后进入冷却 |

## 2. 同步基准

不直接比较两条轨道的绝对 `currentTime`。每次开始播放、继续播放或手动跳转时，记录两条轨道当时的播放位置作为本次播放段的起点：

```text
伴奏相对时长 = 伴奏当前时间 - 伴奏同步起点
干声相对时长 = 干声当前时间 - 干声同步起点
误差 = 伴奏相对时长 - 干声相对时长
```

这样处理后，即使两条轨道的总时长不同，也只比较它们在当前播放段中已经播放了多长时间，不要求总时长一致。

## 3. 分级校正

### 3.1 小误差

误差在 `±5ms` 以内时认为已经达到目标，不修改干声轨播放状态。

### 3.2 中等误差

误差超过 `±5ms` 但未超过 `±200ms` 时，全部通过干声轨 `playbackRate` 短时追赶或等待，偏差越大，一次调整的幅度越大：

- 伴奏相对时长更大：干声轨加速
- 干声相对时长更大：干声轨减速
- `5~10ms`：调整 `1%`
- `10~50ms`：调整 `3%`
- `50~100ms`：调整 `6%`
- `100~200ms`：调整 `10%`

相比频繁 seek，短时变速可以减少可听见的跳变。

### 3.3 大误差

误差超过 `±200ms` 时，将干声轨 seek 到当前播放段应有的相对位置：

```text
目标干声位置 = 干声同步起点 + 伴奏相对时长
```

目标位置会限制在干声轨总时长范围内。原生 `HTMLMediaElement` 的 seek 是异步操作，因此硬重同步采用串行状态机：

1. 第一次满足硬重同步条件时发起 seek，并进入“重同步中”。
2. 收到 `seeked` 前，所有后续硬重同步请求都会被合并，不会发起第二次 seek。
3. 收到 `seeked` 后进入 `1s` 冷却期；冷却结束后才允许新的硬重同步。
4. 若 `1.5s` 内未收到 `seeked`，也进入同样的冷却期，避免异常媒体持续重试。

因此，短时间内多次发现大偏差时，用户最多听到一次跳变，随后由变速校正继续收敛，不会出现每隔数百毫秒重复 seek 的卡顿。

## 4. 不同总时长的处理

干声轨接近结尾或已经结束时，停止对干声轨进行播放速率校正和 seek：

- `media.ended` 为真时停止同步干预
- 干声轨距离结尾小于 `10ms` 时停止同步干预

这可以避免伴奏继续播放时，伴奏相对时长持续增长，导致系统不断尝试把干声轨 seek 到其不存在的后续位置。

## 5. 播放生命周期

- 开始播放：先记录临时同步起点并将干声轨播放速率恢复为 `1.0`；两条轨道的 `play()` 都成功后，再记录一次实际播放起点，避免起播瞬时偏差触发硬重同步
- 暂停后继续：重新记录当前播放位置作为新的同步起点
- 手动跳转：两条轨道跳转后重新记录同步起点
- 任一轨道结束：由伴奏轨的结束事件结束整体播放状态

同步期间使用 `_syncing` 防止校正 seek 触发另一条轨道的交互同步，避免两条轨道互相拉扯。

## 6. 已知限制与后续观察

1. 浏览器 `HTMLMediaElement.currentTime` 和设备音频时钟存在抖动，不能把 `5ms` 误差当作每帧都必须修正的硬触发条件。
2. 当前以伴奏轨的播放事件作为同步检查时机；不同设备的音频输出延迟仍可能造成实际听感差异。
3. 如果实测仍有明显抖动，应优先观察硬重同步是否在 `seeked` 后仍不能收敛，再结合实际音频编码和输出设备延迟调整 `±200ms` 阈值、变速范围或冷却时间。

## 7. 问题复盘：重复 seek 导致播放卡顿

### 现象

部分歌曲在播放时持续输出类似日志：

```text
vocal immediate resync drift(ms) 80
```

日志在短时间内反复出现，干声轨随之不断卡顿。虽然每次都尝试重同步，但偏差没有明显降低。

### 根因

旧实现只用 `300ms` 时间间隔限制硬重同步。调用 `wsVocal.seekTo()` 后会立即解除代码层的同步锁，但底层 `HTMLMediaElement` 的 seek 是异步完成的。

当人声轨尚在定位或解码时，下一次同步检查又会判断偏差超过阈值并发起新的 seek，覆盖前一次定位。结果是干声轨无法连续推进，固定在相近误差附近反复触发重同步。

### 修复与验证

- 使用 `seeked` 事件作为一次硬重同步完成的唯一信号；完成前合并所有后续 seek 请求。
- 将 `5~200ms` 偏差按四档通过 `playbackRate` 平滑追赶，避免 `80ms` 一类偏差直接跳播，同时继续向 `±5ms` 目标收敛。
- `seeked` 后冷却 `1s`；seek 超过 `1.5s` 未完成时也进入冷却，避免异常音频无限重试。
- 新增 `VocalResyncGate` 单元测试，验证重复请求合并和超时冷却行为。
